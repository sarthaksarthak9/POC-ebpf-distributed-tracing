# Tracing POC: Node.js with OpenTelemetry eBPF Instrumentation

A sample Node.js service traced by OpenTelemetry eBPF Instrumentation (OBI), with nothing added to
the application, its pod or its Deployment

## Summary

**What we did.** We ran the Node.js 21 service on a local kind cluster
(Kubernetes 1.34, host kernel 6.8.0-138 with Secure Boot on), with OBI v1.0.0 as a DaemonSet that
selects pods by namespace. The application has no tracing annotations, and its start script
overwrites `NODE_OPTIONS` on purpose. Traces went to a local Jaeger standing in for the Tier 2
collector.

**Findings.**

| # | Finding | Evidence |
|---|---|---|
| 1 | Nothing changes on the application side | No annotation, init container, environment variable, image or start-script change; the pod spec is exactly as deployed |
| 2 | A start script that overwrites `NODE_OPTIONS` is still traced | `NODE_OPTIONS=--max-old-space-size=256` only, and every request traced. This case drops the operator's agent |
| 3 | An operator that enforces its Deployment sees no drift | Reconciler "in sync" throughout, Deployment generation 1, 0 restarts, pod traced. No change to the operator's spec |
| 4 | Each service call is captured with the right labels | Server and client spans per request; `service.name` from the Deployment; `k8s.*`, `deployment.environment` and `site` set once on the DaemonSet |
| 5 | **Cross-service context propagation did not work on this host** | OBI disabled it at start: this kernel has a socket bug (FIONREAD in a sockhash), and the fix OBI loads for it is blocked by Secure Boot's kernel lockdown. Each `/api/chain` became two traces, with `/api/hello` on its own. Same with `all`, `tcp` and `headers` |
| 6 | Node.js needs `SYS_ADMIN` | Without it, OBI cannot enter the pod's network namespace: "trace-context propagation and nodejs runtime metrics will not work for NodeJS services". The docs say only Go needs it |
| 7 | Propagation is off by default | `ebpf.context_propagation` must be set, or every hop is a separate trace |
| 8 | Calls a process makes to itself on `localhost` are joined anyway | `managed-app` calls itself on `localhost`: one 5-span trace. OBI sees both ends of the connection, so this is not propagation and says nothing about calls between pods |
| 9 | OBI needs host-level access | `hostPID`, `hostNetwork`, and eight capabilities including `SYS_ADMIN` and `NET_ADMIN` (not `privileged: true`). Policies that restrict these will block it |
| 10 | Memory cost is per node, and not small | OBI used about 250 MB and under 0.5% CPU, against about 10–14 MB for each application pod |
| 11 | Probes and request phases add spans | Each readiness probe is a 3-span trace (58 in 10 minutes for one pod); every request also carries `in queue` and `processing` spans |

**Not yet tested:** propagation on a kernel without lockdown (the deciding test), the IPSL node
kernels, HTTPS between services, the path to Tier 2, more than one node, and services that also
run the operator's agent (OBI skips those by default).

| File | What it is |
|---|---|
| `app.js` | API on port 3000: `/api/hello`, and `/api/chain`, which calls `/api/hello` over the Service |
| `entrypoint.sh` | Start script that echoes, loads a simulated secret, overwrites `NODE_OPTIONS`, then runs `node` |
| `app.yaml` | Deployment (stock `node:21-alpine`, code from a ConfigMap, no tracing annotations) and Service |
| `obi.yaml` | OBI namespace, read-only RBAC, config (namespace `ebpf-poc`, propagation on, 100% sampling) and DaemonSet |
| `jaeger.yaml` | Jaeger all-in-one, standing in for Tier 2 |

No image is built: the code and script are mounted from a ConfigMap generated by
`kustomization.yaml`.

## Why propagation failed here

OBI joins two services into one trace by writing `traceparent` into outgoing requests from the
kernel. On kernels that carry a particular socket fix (6.6.128+, 6.12.75+, 6.18.14+, 6.19+, and
distribution kernels that backported it, such as this 6.8.0-138), that injection can make
applications that size reads with `FIONREAD` stall. OBI loads a correction for it, which needs the
`bpf_probe_write_user` helper. Kernel lockdown in `integrity` or `confidentiality` mode, which
Secure Boot turns on, blocks that helper. OBI then turns propagation off rather than risk the
applications.

So whether OBI can produce connected traces depends on each node's kernel and lockdown state, not
on Kubernetes or the application. To check a node:

```bash
uname -r
cat /sys/kernel/security/lockdown    # [none] is needed
mokutil --sb-state                   # SecureBoot disabled, or lockdown set to none
```

At start, OBI logs `context propagation is disabled` when it cannot propagate.

## Compared with the operator

| | Operator (Node.js SDK) | OBI (eBPF) |
|---|---|---|
| Change per service | Two pod annotations | None; selected by namespace or label in OBI's config |
| Start scripts | Must keep `NODE_OPTIONS` | Not affected |
| Operator-managed services | Annotations go through the operator's spec | No change |
| Connected traces across services | Yes | Only where the node's kernel allows propagation (finding 5) |
| HTTPS between services | Yes | Only between OBI-instrumented services (per the docs; not tested) |
| Custom spans and attributes | Yes, with the SDK | No |
| Runs as | Init container and agent in each pod | One DaemonSet per node, with host access (finding 9) |

## Deploy

This runs on any cluster whose nodes allow eBPF. Locally, kind uses the host's kernel:

```bash
kind create cluster --name ebpf-poc
kubectl apply -f obi.yaml -f jaeger.yaml
kubectl -n obi rollout status ds/obi
kubectl apply -k .
kubectl -n ebpf-poc rollout status deployment/ebpf-poc-app
```

On a real cluster, point `otel_traces_export.endpoint` in `obi.yaml` at Tier 2,
`http://10.185.13.105:4318`, and leave out `jaeger.yaml`.

## Verify

The pod is unchanged:

```bash
kubectl -n ebpf-poc get pod -l app=ebpf-poc-app -o jsonpath='init=[{.items[0].spec.initContainers[*].name}] annotations={.items[0].metadata.annotations}{"\n"}'
```

Expected: `init=[] annotations=`.

OBI found the process and could inject into Node.js:

```bash
kubectl -n obi logs ds/obi | grep -E 'instrumenting process|Script successfully injected|propagation is disabled'
```

Expected: `instrumenting process ... type=nodejs` and `Script successfully injected`. If
`context propagation is disabled` appears, the node fails the check above.

Send requests:

```bash
kubectl -n ebpf-poc exec deploy/ebpf-poc-app -- wget -qO- http://localhost:3000/api/chain
```

Then open Jaeger and search for service `ebpf-poc-app`:

```bash
kubectl -n obi port-forward svc/jaeger 16686:16686
```

With propagation working, each `/api/chain` request is one trace: the server span for
`/api/chain`, the client call to `/api/hello`, and the server span for `/api/hello`. Without it,
the `/api/hello` server span is a separate one-span trace.

## Applications managed by another operator

`operator-case/` reuses the stand-in from the operator POC: every 15 seconds it compares the
pod-template annotations of `managed-app` with its desired spec and replaces the Deployment on any
difference. The desired spec has nothing added for tracing.

```bash
kubectl apply -k operator-case/
kubectl -n ebpf-poc logs -f deploy/poc-reconciler
```

Expected: `in sync` with `init=[]` and `restarts=0` on every cycle, and `managed-app` in Jaeger.

## Clean up

```bash
kubectl delete -k operator-case/
kubectl delete -k .
kubectl delete -f obi.yaml -f jaeger.yaml
kind delete cluster --name ebpf-poc
```
